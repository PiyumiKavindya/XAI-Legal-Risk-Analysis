# **Semester 1 — Detailed Weekly Teaching and Expected Outputs**

## **S1 W1 — Project initiation, research orientation and assessment roadmap**

* Understand the complete Computer Science and Software Engineering Project lifecycle and the relationship between PP, IPD and the Final Project.  
* Distinguish software development, research, and research-led software development.  
* Identify the project problem/domain, anticipated contribution, feasibility and initial scope.  
* Introduce supervision expectations, research ethics, participant/data issues, responsible AI, intellectual property and research integrity.  
* Expected output: Title → Domain → Initial Problem → Proposed Direction → Scope → Literature Search Terms → Ethics Classification.

## **S1 W2 — Problem formulation, research questions, aim and objectives**

* Distinguish Problem Statement ≠ Research Gap ≠ Research Question.  
* Develop the problem statement, research gap, research question(s), aim, measurable objectives, success criteria and anticipated contribution.  
* Distinguish research objectives from implementation objectives.  
* Introduce the traceability chain: Problem → Gap → RQ → Aim → Objectives → Requirements → Design → Implementation → Testing/Evaluation.

## **S1 W3 — Literature Review and Background Review**

* Cover academic database searching, search strategies, source quality, citation chaining, seminal versus recent literature and critical reading.  
* Use a Literature Survey Matrix and thematic synthesis rather than paper-by-paper description.  
* Compare existing systems, technologies, datasets, algorithms/models and reported limitations.  
* Use the literature to construct and justify the research gap.

## **S1 W4 — Stakeholders, Requirements Elicitation and Requirements Analysis**

* Identify stakeholders, interests, influence and roles.  
* Select and justify suitable elicitation techniques and evidence-collection methods.  
* Analyse elicitation evidence and translate it into functional and non-functional requirements.  
* Create requirements-to-objectives traceability.  
* By this point, students should have enough material for a meaningful 19 October formative PP submission.

## **19 October — Formative PP submission**

* The submission is formative: Supervisor → Feedback → Improvement. It is not marked.  
* Expected draft evidence includes problem, literature/background review, gap, RQs, aim/objectives, proposed contribution, methodology, requirements work, datasets/data strategy where applicable, preliminary architecture, tools/algorithm considerations, baseline/evaluation plan, ethics, project plan, draft handout and draft presentation.

## **S1 W5 — Use Cases, Requirements Modelling, System Context and Architecture Foundations**

* Develop the Context Diagram, Use Case Diagram and Use Case Descriptions.  
* Use Activity, Sequence, State or Data Flow models only where appropriate.  
* Make requirements atomic, measurable, testable, unambiguous, uniquely identified and prioritised.  
* Build traceability from Requirement → Objective and, where possible, Gap → RQ → Objective → Requirement → Component → Evaluation.

## **S1 W6 — Technology Selection, Methodology, Project Planning and PP Construction**

* Compare technology alternatives using explicit criteria and justify the final selection.  
* Define research methodology, experimental methodology, data collection, development methodology and evaluation planning.  
* Create WBS, milestones, dependencies, Gantt chart, risks and resource plan.  
* Consolidate the PP handout, presentation, citations, research argument and defence preparation.  
* By the end of this week, students should have a complete PP draft.

## **5 November 2026 — PP summative submission**

* Final PP submission for assessment and marking. Students should submit the prescribed PP components and ethics documentation.

## **S1 W7 — PP assessment and transition**

* No separate Week 7 teaching topic is specified in the teaching schedule.  
* Use the week for PP assessment/defence and immediate transition to implementation.  
* Students should begin repository setup, data acquisition, baseline preparation, core technical investigation and proof-of-concept work rather than waiting for PP marks.

## **S1 W8 — From PP to IPD: Formal Requirements and System Architecture**

* Formalise requirements and move from proposal to technical execution.  
* Develop logical, physical/deployment and data architecture, components, interfaces and ML/model pipelines where applicable.  
* Establish architecture-to-requirement traceability and an implementation backlog.  
* Expected output: Architecture V1 \+ Implementation Backlog V1 \+ PP Action List.

## **S1 W9 — Implementation Engineering and Prototype Development**

* Distinguish prototype, mock-up and MVP.  
* Prioritise Must-Have functionality and the research-critical component.  
* Use Git/source control, coding standards, technical documentation, reproducibility and dependency/experiment management.  
* Start with technically risky or research-critical functionality rather than peripheral UI features.

## **S1 W10 — Testing, Experimental Design and Evaluation Strategy**

* Define software testing and research evaluation before implementation is complete.  
* Cover baselines, data splits, metrics, cross-validation, benchmarking, ablation, hyperparameter tuning, error analysis, robustness and statistical analysis where relevant.  
* Use the chain: Research Question → Evaluation Question → Metric → Experiment → Evidence → Conclusion.

## **S1 W11 — IPD Readiness \+ Final Report Forward Planning**

* Review stakeholder analysis, FR/NFR, implementation status, architecture, deployable/hosted prototype where appropriate, schedule and demonstration evidence.  
* Introduce the final-report evidence requirements so students know what to accumulate during development.  
* Create a PP Feedback Action Matrix: Feedback → Required Change → Student Action → Evidence → Completion Date.  
* Complete an IPD readiness review and a December–January weekly development plan.

## **S1 W12 — Independent development / IPD preparation**

* No new formal teaching topic is specified in the schedule.  
* By the end of Semester 1, requirements should be substantially stable, architecture defined, implementation underway, the research core started, and the evaluation plan established.  
* Students should leave with clear IPD targets and a detailed December–January implementation plan.

## **December 2026–January 2027 — Independent implementation sprint**

* Continue: Implementation → Baselines → Proposed Research Component → Experiments → Testing → Evidence → IPD.

# **Semester 2 — Detailed Weekly Teaching and Expected Outputs**

## **S2 W1 — IPD Finalisation Clinic**

* Verify stakeholders, requirements, architecture, schedule deviations, recovery actions, working prototype, deployment/hosting and video evidence.  
* This is a finalisation week, not the point at which students should begin building the prototype.

## **28 January 2027 — IPD summative submission**

* Final IPD submission for assessment and marking. The work should evidence actual technical/research progress rather than another proposal.

## **S2 W2 — IPD Submission Week \+ Final Project Gap Analysis**

* Identify unimplemented requirements, incomplete experiments, missing datasets/data, incomplete tests, literature gaps, technical gaps, methodological gaps, ethics gaps and incomplete report chapters.  
* Expected output: Final Project Gap Analysis \+ Completion Plan.  
* Students continue working immediately rather than waiting for the IPD result.

## **S2 W3 — Research and Development Methodology**

* Cover research strategy, experimental design, data collection, sampling, datasets, preprocessing, model/algorithm selection, development methodology, requirements methodology, design methodology and testing methodology.  
* Address validity, reliability and reproducibility.  
* Every methodological decision should be justified, not merely described.

## **S2 W4 — Design and Traceability**

* Finalise overall architecture and detailed technical design.  
* Cover algorithms/models, database design, data design and interaction design where applicable.  
* Justify alternatives and rationale.  
* Maintain traceability: FR/NFR → Design Component → Implementation → Test.

## **S2 W5 — Tools and Implementation**

* Explain tools and alternatives, implementation decisions, algorithms, important code, technical challenges and solutions, frameworks/libraries, adapted/external code and the student-developed contribution.  
* Clearly distinguish what already existed from what the student developed or contributed.

## **18 February — IPD marking completion / 25 February — feedback release**

* All marking and feedback should be completed by 18 February.  
* Formal IPD marks and feedback are released to students by 25 February and become the final major formal feedback point before the Final Project.

## **S2 W6 — Testing and Experimental Evaluation**

* Cover unit, integration and system testing; requirements validation; baseline evaluation; comparative experiments; metrics; robustness; error analysis; statistical analysis; usability evaluation where appropriate; and reproducibility.  
* Core question: Does the evidence actually allow the student to answer the research question?

## **S2 W7 — Critical Analysis, Research Findings and Contribution**

* Interpret results rather than merely reporting numbers.  
* Compare findings with the literature and explicitly answer research questions.  
* Discuss strengths, weaknesses, validity threats, limitations, generalisability and contribution to knowledge/practice.

## **S2 W8 — Introduction, Background, Ethics and Conclusions**

* Revisit the beginning of the dissertation after the research has produced evidence.  
* Finalise the problem, aim, objectives, literature, existing systems, research gaps and legal/ethical/social/professional/security considerations.  
* Finalise objective evaluation, answers to RQs, contribution, limitations, future work and reflection.

## **S2 W9 — Full Dissertation Integration and Quality Assurance**

* Conduct the alignment audit: Problem → Gap → Research Question → Aim → Objectives → Requirements → Design → Implementation → Testing → Results → Conclusion.  
* Check report structure, academic argument, academic language, figures, tables, cross-referencing, Harvard referencing, appendices, attribution, academic integrity and proofreading.  
* Key milestone: Full Report Draft \+ QA Review.

## **S2 W10 — Final completion week**

* No new formal teaching topic is specified. Use the week for final implementation, final experiments and report completion.  
* Avoid introducing new major features immediately before submission unless absolutely necessary.

## **S2 W11 — Final Project Submission \+ Viva Preparation**

* Perform final checks on report, code, repository, implementation, deployment, evidence, ethics and recorded demonstration.  
* Prepare for viva: concise research explanation, live demonstration, architecture defence, methodology defence, code defence, results defence, limitations, contribution and future work.  
* Final supervision milestone: identify remaining critical gaps and submission priorities.

## **5 April 2027 — Final Project submission**

* Submit the required final artefacts: Final Project Report \+ Code/implementation artefacts \+ Recorded Demonstration.

## **S2 W12 — Pre-viva preparation**

* No new teaching content is specified. Students prepare for the viva while examiners and supervisors independently review the submitted artefacts.
